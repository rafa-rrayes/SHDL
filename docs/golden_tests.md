# The SHDL Golden Test Suite

*The complete verification program for the SHDL project: what must be tested, how it is verified,
what is already covered, and what remains. Companion to `SHDL_Project.md`, `shdl.md`,
`base_shdl.md`, and `shdlc_goals.md`.*

---

## 0. Purpose

SHDL's project principles demand **correctness before performance** and a test corpus mature
enough that the flattener and compiler can be refactored or reimplemented with confidence. This
document defines the **golden test suite**: the closed list of obligations that, when all green,
justify the claim *"SHDL contains no known bugs and no untested normative behavior."*

"Extremely certain" is operationalized as five concrete conditions:

1. **Spec closure** — every normative statement in `shdl.md`, `base_shdl.md`, and
   `shdlc_goals.md` maps to at least one test (this document is that mapping).
2. **Diagnostic closure** — every diagnostic *raise site* (not just every code) is exercised by
   at least one test asserting code, message substance, and position.
3. **Oracle closure** — every executable artifact is validated bit-exactly, cycle-by-cycle,
   against an independent reference, on fixed corpora *and* randomized inputs.
4. **Crash closure** — no user input, however malformed, produces an uncaught Python exception,
   a C compiler error, or undefined behavior; failures are always structured diagnostics.
5. **Determinism closure** — byte-identical Base SHDL, byte-identical generated C, identical
   traces: across runs, hash seeds, optimization levels, build modes, and platforms.

Each domain below lists its obligations with stable IDs. Status legend:
**✅ covered** (exists today) · **🟡 partial** (exists, with named holes) · **❌ missing** ·
**⚪ blocked** (component not yet built; obligation defined now, activated at build time).

## 1. Verification Architecture

### 1.1 The oracle chain

The suite's trust argument rests on independent implementations checking each other:

```
  shdl.md + base_shdl.md (specs; human-verified examples base_shdl §3.7/§4.4)
      │  pinned literally by test_spec_examples
      ▼
  HighEval ── high-level interpreter (runs phase-3 output: pre-expander SHDL)
      │  trace equality on random + exhaustive stimulus (test_equivalence)
      ▼
  BaseEval ── reference interpreter for Base SHDL (THE ground truth, §7.1 shdlc_goals)
      │  lockstep differential, every port, every cycle (DualSim)
      ▼
  Compiled C library (release; later: debug build, optimization tiers, backends)
      │  replayed bit-exactly against (traces sourced from BaseEval, never from C)
      ▼
  Conformance corpus (v1.1.0 — 38 cases / 40 traces, provenance: never from C)
```

Independence rules (already in force, must never be weakened):
- Conformance traces are generated by **OracleSim (BaseEval)** only — never by the C
  implementation under test.
- `expected.base.shdl` files are frozen flattener output with pinned timestamps; regeneration is
  a deliberate, reviewed, manifest-versioned act, never a side effect of a failing test.
- Every future backend/tier validates against **both** the corpus and live BaseEval lockstep.

### 1.2 Test tiers

| Tier | Name | Contents | When it runs |
|------|------|----------|--------------|
| T0 | Unit | lexer/parser/phases/codegen unit tests, diagnostics matrix | every commit, seconds |
| T1 | Property | invariants over generated inputs (order independence, idempotence, no-crash) | every commit |
| T2 | Differential | DualSim fixtures, fuzz circuits, opt-level/build-mode equivalence | every commit (small N), nightly (large N) |
| T3 | Conformance | frozen corpus, Tier A byte-equality + Tier B/C trace replay | every commit |
| T4 | Acceptance | SR16 CPU lockstep vs golden model, real programs | every commit (cached builds) |
| T5 | Soak / fuzz campaign | env-scaled long runs (`SHDLC_FUZZ=500`, `SHDLC_DIFF_CYCLES=5000`), sanitizer builds | nightly / pre-release |

### 1.3 Standing enforcement mechanisms (keep forever)

- **Diagnostics completeness assertion** (`test_diagnostics_matrix`): the set of tested codes
  must equal the `ErrorCode` enum — a new code cannot land untested. *Extend* (see DIA-2) to
  per-raise-site coverage.
- **STRICT_CFLAGS** (`-std=c11 -Wall -Wextra -Werror -pedantic -O2 -fPIC -shared
  -fvisibility=hidden`): every harness-driven generated-C build in the suite is a zero-warning
  proof. (The CLI subprocess tests build with release `DEFAULT_CFLAGS`, which carry no warning
  flags — the CCT-3 hole.)
- **Corpus integrity test**: manifest↔disk bijection, feature-coverage check, minimum case count
  guard (≥38 Tier A, ≥40 traces) plus per-golden content hashes (CNF-9 drift fence) so silent
  corpus loss or coordinated regen fails loudly.
- **Seed-stable randomness**: all randomized tests derive seeds from fixture names
  (`zlib.crc32`), and failures embed the full netlist/action log for replay.

## 5. Suite policy

1. **Tests are the spec's enforcement arm.** When a test pins previously ambiguous behavior, the
   spec is amended in the same change. No "tested but undocumented" semantics.
2. **Regeneration discipline.** Conformance artifacts regenerate only via the dedicated script,
   with a manifest version bump and changelog entry; CI rejects drift (mechanism: CNF-9 — today
   this policy has no enforcement hook).
3. **The completeness assertions are sacred** (diagnostics enum match, corpus minimum counts,
   STRICT_CFLAGS). They are the mechanisms that keep this document true over time; extending
   them (per-site matrix, W-codes) is preferred over adding unenforced conventions.
4. **Randomized ≠ flaky.** All fuzz/differential tests are seed-stable per fixture and embed
   replay artifacts in failure output. A fuzz failure is a permanent regression test candidate:
   minimize and freeze it into the corpus.
5. **Oracles stay strict.** BaseEval may be stricter than the C ABI (e.g., raising on overflow
   where C masks). Harnesses bridge deliberately (DualSim masks for the oracle); never relax the
   oracle to match the implementation.
6. **One lesson, one test.** Every bug found in the wild (e.g., the SRLatch power-on fixed-point
   incident) lands a minimal pinned regression in the most upstream suite that can express it,
   plus a conformance case if observable in traces.

## 6. Exit criteria

The golden suite is **complete** when: every row in Domains A–T and W is ✅ (the per-component
rows — CNF-5 (PySHDL wired 2026-06-12; debug build / backends / tiers still open), ABI-18 —
convert and close per component under Domain V); every AMB row has
decision+amendment+test; P0 and P1 registers are empty; CI runs T0–T4 on Linux+macOS per commit
and T5 nightly; and the coverage gate holds. At that point — and only then — the project's
"correct first, fast last" mandate permits Layer-7 optimization work, with this suite re-run
bit-exactly per tier as the unchanging gate.
